# Code review, 2026-10-16

A findings-only review pass (Opus 5.5) over the whole codebase at commit `5bfd569`. Nothing in the code was changed.
The first part is in plain words; the detail for whoever fixes things follows.

## Status

- **Fixed:** 1-3 (commit `0226895`), 4-6 (the commit after it). While doing 5, a further bug turned up and was
  fixed: `sw_verify::decoded_order` assumed the wrong FFmpeg order for 7.1 (rears before sides), and matching channels
  by content cannot tell apart two channels that carry nearly the same audio, so the queue's lossy check compares
  each channel with the decoded channel FFmpeg's order names (`Source::order_known`).
- **Open:** 7-12, and confirming 4 by eye in an installed release build.

## The short version

- **The project is in good health.** Clippy is clean, all 332 tests pass (1 ignored), and the verifier held up when I
  fed it 40 deliberately damaged files (cut short, random bytes flipped): no crashes, and it flagged every one as
  failed, while the four undamaged originals passed.
- **One real bug I could reproduce:** if you use **Normalise** or **Delay** on a lossless format (TrueHD, MLP, DTS-HD
  MA) with verification on, the job is reported as **Failed**, even though the file it wrote is fine. The checker
  compares the encode with the *untouched* source, so the gain or delay looks like damage.
- **One real bug found by reading (not run):** two **Dolby engine** jobs running at the same time in the queue share
  one work folder, so the second can delete the first one's files halfway through.
- **One robustness gap:** if an encoder ever crashes (a "panic") inside the app's queue, that job stays "Encoding"
  forever and takes up a queue slot until the app is restarted. With 1 job at a time, the whole queue stops.
- **Likely annoyance to check in the installed app:** every FFmpeg run (verify, preview, file info, FFmpeg-engine
  encodes) probably flashes a black console window, because only the Dolby engine calls hide theirs.
- The rest is smaller: a weak check for lossy formats, preview oddities with Normalise/Delay, a loudness weighting
  detail, some safety hardening in the app, and tidy-ups.

## Findings, most important first

Each has: what is wrong, how sure I am, and what to do.

### 1. Lossless verify fails after Normalise or Delay (confirmed)

- Where: `crates/sw-queue/src/run/mod.rs:149` (verify runs whatever the gain/delay),
  `crates/sw-backend-ffmpeg/src/lib.rs:365` (lossless check = MD5 of FFmpeg's read of the *raw* inputs vs the decode).
- What happens: Normalise applies a gain and Delay shifts the audio as the samples are read
  (`StemSet::set_gain_db`, `set_delay_frames`); the FFmpeg check knows neither, so the MD5s never match.
- Reproduced with the T1 5.1 set, TrueHD, `subwoofa run JOB.json --verify`: plain job "verified"; with
  `--normalize -31` and with `--delay-ms 20` both "FAILED: decoded audio differs from source".
- Why the tests missed it: every normalise/delay test in `sw-queue/tests/compare.rs` calls `execute(.., false, ..)`
  (no verify).
- Fix: when a gain or delay is set, verify with `sw_verify::compare_with_source`-style logic against the processed
  source (or skip the MD5 check and say why in the log), and add a test with `verify = true` for each.

### 2. Two Dolby engine jobs at once share a work folder (high confidence, not run)

- Where: `crates/sw-queue/src/dolby.rs:102` names the folder `{tag}{process id}`, so every queue job uses
  `%TEMP%\...\encode<pid>`; `crates/sw-backend-dee/src/taskrun.rs:114-118` empties `in/`, `out/`, `temp/` at the start
  and `:150-152` at the end.
- What happens: with queue concurrency 2+ and two `--engine dolby` jobs, the second wipes the first's staged inputs and
  output while the engine is using them; the first then fails or, worse, picks up the other job's result.
- Fix: add the job id (or a counter / random suffix) to the folder name. Cheap.

### 3. A panic in a queued job jams the queue (high confidence, not run)

- Where: `crates/sw-queue/src/lib.rs:283`: `run::execute` is called on a plain worker thread with no `catch_unwind`.
- What happens: the thread dies, the job stays `Running`, and `running < concurrency` never frees that slot. With
  concurrency 1, nothing else ever starts. The code already expects panics elsewhere (`sw-verify/src/thd.rs:579` wraps
  the TrueHD analyser in `catch_unwind`).
- Fix: wrap the call in `std::panic::catch_unwind(AssertUnwindSafe(..))` and turn a panic into `Failed` with a message
  ("internal error in the encoder, please report"). Same for the preview and Dolby command threads in the app.

### 4. Console windows flashing in the installed app (likely; confirm in a release build)

- Where: the release app is a Windows GUI program (`app/src-tauri/src/main.rs:1`). Only `sw-backend-dee` and
  `toolpaths.rs` set `CREATE_NO_WINDOW` (`0x0800_0000`). FFmpeg/ffprobe are started without it in
  `sw-backend-ffmpeg/src/lib.rs`, `sw-verify/src/source.rs`, `sw-verify/src/deep/*`, `sw-tools/src/check.rs` and
  `app/src-tauri/src/sources.rs` (`probe`).
- What happens: Windows gives each console child of a GUI app its own visible console window, so verify, preview,
  file info and FFmpeg-engine encodes may each flash a black window.
- Fix: one small helper (e.g. `sw_core::process::quiet(Command)`) that sets the flag on Windows, used everywhere.

### 5. Lossy verify only checks that FFmpeg decodes without errors (confirmed by reading)

- Where: `crates/sw-backend-ffmpeg/src/lib.rs:376-396`; the length check is stubbed (`let _ = expect_secs;`).
- What happens: a lossy encode that is short, silent, has swapped or missing channels still shows "Passed" in the
  queue. Subwoofa already has the right tool (`compare_with_source`: line-up, channel matching, per-channel SNR); the
  queue just does not use it.
- Fix: for AC-3/E-AC-3/DTS core/HRA/Express, run the source comparison and warn below a sane SNR or when length
  differs by more than one frame. It costs one extra decode.

### 6. Preview with Normalise or Delay is misleading (high confidence, not run)

- Where: `crates/sw-queue/src/preview.rs:61` encodes the excerpt with `execute`, which applies the job's gain/delay;
  the source side of the comparison (`open_sources`, line 47) has neither.
- What happens: (a) Normalise measures only the 20 s excerpt, so the preview's gain is not the gain the real job will
  use; (b) the gain shows up as "noise": SNR and the difference file are dominated by a level change; (c) a delay longer
  than `MAX_LAG` (16384 samples, 0.34 s at 48 kHz) makes line-up fail, so the preview errors out.
- Fix: measure the gain on the whole span once and pass it in; apply the same gain/delay to the source side (or switch
  both off for the preview and say so).

### 7. Loudness weighting of height and rear channels (certain about the spec; impact small)

- Where: `crates/sw-loudness/src/meter.rs:25` gives the +1.5 dB surround weight to `Tsl Tsr Tbl Tbr Tbc` (heights)
  and `Lsr Rsr Cs` (rear).
- BS.1770-4 gives 1.41 only to channels within 30 degrees of ear height and 60-120 degrees to the side; everything
  else is 1.0. Heights are clearly over-weighted; rear surrounds are a judgement call (many meters weight all
  surrounds in 7.1 the same).
- Effect: Measure / auto-dialnorm / Normalise read slightly loud on 7.1.4, 9.1.6, 22.2 programmes with busy heights.
- Fix: weight the heights 1.0; compare 7.1 against `subwoofa loudness --dolby` (Dolby's meter) to settle the rears.

### 8. App hardening (low risk today, cheap to fix)

- `tauri.conf.json`: `"csp": null` with `withGlobalTauri`, and the commands `write_text` / `read_log`
  (`app/src-tauri/src/jobs.rs:30-37`) read and write **any** path. That is fine while nothing untrusted reaches the
  page as HTML, but the queue list puts `j.name` and the first line of `j.message` into `innerHTML` unescaped
  (`app/ui/job.js:197`). Messages carry FFmpeg/engine text and file names. Windows forbids `<` `>` in file names,
  so a real attack is unlikely; a stray `<` would still break the row.
- Fix: use the existing `esc()` (from `verify.js`) there and in `layout.js`/`settings.js`/`streamtools.js`; set a
  simple CSP (`default-src 'self'; style-src 'self' 'unsafe-inline'`); optionally limit `read_log` to `*_log.txt`.

### 9. Unsound `unsafe` in `with_threads` (works today; wrong in principle)

- Where: `crates/sw-queue/src/threads.rs:17` (`unsafe impl<T> Send for Unchecked<T>`).
- Moving a non-`Send` value to another thread is undefined behaviour even if only one thread touches it at a time
  (thread-bound values such as `Rc` or a `MutexGuard` break). Today the captured values are all really `Send`.
- Fix: add `+ Send` to the progress callback types (`&mut (dyn FnMut(f32, bool) + Send)`) and drop the `unsafe`.

### 10. Dolby staging can copy whole stems onto the nearly full C: drive

- Where: `sw-backend-dee/src/taskrun.rs:29-30`: hard link first, copy if that fails. Hard links only work on the same
  drive, and the work folder is `%TEMP%` (C:). Inputs on O:/F: are therefore **copied** to C: for every Dolby job
  (a 2 h 5.1 24-bit film is ~6 GB).
- Fix: prefer a space-free work folder on the same drive as the inputs (e.g. `<drive>:\subwoofa-dee`), falling back
  to `%TEMP%`; and check free space before copying.

### 11. TrueHD peak data rate is stated, never measured (to check)

- `crates/sw-codec-truehd/src/sync.rs:21` always writes a 9.6 Mbit/s peak rate into the major sync, and nothing
  checks the actual rate against it (or against Blu-ray's 18 Mbit/s limit). Dense 7.1/96 kHz material could exceed
  the stated figure, which strict authoring tools or players may reject.
- Next step: compare our field with Dolby's on the same 7.1 source (`subwoofa stream-info`), measure our real peak
  over the decoder's buffer window, and add a "Peak data rate" check to `sw-verify/src/thd.rs`. Same idea for the
  DTS-HD MA 24.5 Mbit/s Blu-ray limit.

### 12. Smaller items

- `sw-verify/src/source.rs:70`: lossless vs lossy is guessed by searching the format **name** for words like "wav"
  or "pcm" (a DTS-in-WAV report could be judged as lossless). Pass the known `StreamType::is_lossless()` instead.
- `sw-verify/src/source.rs:94`: the decoder's stderr goes to null, so if FFmpeg fails mid-file the user only sees
  "N frames shorter", not why.
- Partial files: a canceled or failed app/CLI encode leaves a half-written file under the final name (only `watch`
  uses a temp name). Write to `.name.partial.ext` and rename on success everywhere.
- `sw-queue/src/run/encoders.rs:376`: the Dolby work folder is removed only on success (the staged sub-folders are
  cleaned either way, so this only leaves empty folders).
- `sw-queue/src/run/sources.rs:34` and `:41`: the same "needs the native engine" check twice.
- Two string literals contain a raw line break instead of `\n` (`run/mod.rs` normalise log line,
  `app/src-tauri/src/streamtools.rs:155`), almost certainly from a heredoc. Harmless but odd.
- The queue orders by `created_ms`; ordering by `id` is simpler and immune to clock changes.
- `sw-pcm` reader: a `bext` chunk shorter than 346 bytes is read past its end (reads the next chunk's bytes as the time
  reference); a WAV with sample rate 0 is accepted (later division by zero, and `find_lag` would loop forever as its
  step becomes 0). Reject both.
- `fetch-ffmpeg.ps1`: forces TLS 1.2 only (`=` instead of `-bor`), and the SHA-256 comes from the same server as the
  zip, so it proves "not damaged" (as the message says), not "not tampered with". Fine for now; say so in the docs.
  It also fails if `ffmpeg.exe` is in use by a running encode.
- **Six bit writers** (`sw-codec-ac3`, `sw-codec-dts` x2, `sw-codec-truehd`, `sw-codec-pcm` x2). They differ in small
  ways: AC-3's `put` does not mask the value in release builds (out-of-range values are only caught by
  `debug_assert`, which tests do run). One shared MSB-first writer in `sw-core` (plus the LE one for Express) would
  be less code and one place to get right. Golden checksums make this a safe refactor.
- Housekeeping: `CLAUDE.md` rule 12 names `Claude Sonnet 5.5` for the commit trailer; the current harness asks for
  `Claude Opus 5.5` in this session (the rule already says to follow the latest reminder).

6. **Hardening (8, 9, 10, partial files)**: escape the queue list, add a CSP, drop the `unsafe`, stage Dolby jobs on
